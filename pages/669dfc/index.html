# 📦 npm 完整使用指南

命令优先、可快速检索的 npm 速用指南。

# 什么是 npm

npm (opens new window)（Node Package Manager）是 Node.js 官方包管理器，覆盖包安装/更新/卸载、依赖与版本管理、脚本运行、包发布、安全审计。

npm -v             # npm 版本
node -v            # Node.js 版本
npm config list    # 当前生效配置
npm -l             # 所有命令用法一览

# 深入理解 npm install

# 安装流程：三棵树的收敛

npm install 本质是把三棵树对齐（npm 内部称为 reify）：依赖树（package.json 声明的）→ 理想树（idealTree，按 semver 应该装什么）→ 实际树（node_modules 里实际装了什么）。展开为五步：

  1. 解析依赖树：读 package.json，按 semver 范围递归计算 idealTree；有 lock 文件则直接按 lock 精确解析，跳过 registry 元数据拉取——这就是 npm ci 更快的根本原因
  2. 下载 tarball：取包元数据（packument）→ 解析 tarball 地址 → 下载 → 校验 sha512 integrity（防篡改）→ 写入缓存 ~/.npm/_cacache（按内容寻址，同一 tarball 全局只存一份）
  3. 扁平化安装：尽量把所有包提升到 node_modules/ 顶层；版本冲突时嵌套进 node_modules/<pkg>/node_modules/
  4. 生成 bin 软链（见下节）
  5. 执行生命周期钩子 → 更新 package-lock.json

# bin 软链机制

包在 package.json 声明 bin 字段（字符串 = 命令名同包名；对象 = 多个命令）：

{ "bin": { "husky": "./bin.js" } }
1

npm install 时在 node_modules/.bin/ 下为它创建可执行软链。bin.js 文件头带 shebang：

#!/usr/bin/env node
1

shell 据此把它交给 node 执行。npm 执行 scripts 时把 node_modules/.bin 注入 PATH 最前面——这就是 scripts 里能直接写 vite / jest / husky 命令名的原因。全局安装（-g）则软链到全局 bin 目录（nvm 管理的 node 不需要 sudo）。

# 生命周期钩子执行顺序

root 包与各依赖包的钩子在安装过程中交错执行：

root preinstall
  → 逐个安装依赖（每个依赖自己的 preinstall → install → postinstall 在此期间执行，
    典型如 node-gyp 编译原生模块）
  → root postinstall
  → root prepare
1
2
3
4
5
钩子 时机 典型用途
preinstall 安装任何依赖前 环境检查
install 依赖安装中 依赖包编译原生模块（node-gyp）
postinstall 依赖装完后 patch-package、初始化
prepare 本地 install 后、装 git 依赖时、publish 打包前 激活 husky

"prepare": "husky" 完整机制（husky 是 CLI 不是函数）：

npm install 装完依赖
  → husky 进入 node_modules/.bin（bin 软链已生成）
  → 自动触发 prepare
  → PATH 含 node_modules/.bin，husky 命令可执行
  → 执行后设置 git core.hooksPath=.husky
  → Git 改从 .husky/ 目录读 hooks
1
2
3
4
5
6

它不是"安装 husky"，而是"依赖装完后运行 husky CLI 激活 Git hooks"——新同事 clone 后只需 npm install，hooks 自动配好。

# 幽灵依赖

扁平化安装的副作用：未在 package.json 声明的包，因被提升到顶层而能被 require（phantom dependency）。隐患：某次上游升级不再提升它，你的代码直接崩。pnpm 用符号链接 + 严格 node_modules 从机制上杜绝此问题。

# 安全：install 脚本即任意代码执行

依赖的 postinstall 可执行任意代码，是供应链攻击的标准入口（如 node-ipc、ua-parser-js 事件）。审计陌生依赖时：

npm i --ignore-scripts    # 跳过所有 install 钩子（副作用：原生模块不编译、husky 不激活）
1

# 版本控制

# 语义化版本

npm 遵循语义化版本 (opens new window)（SemVer，实现为 node-semver (opens new window)），格式 MAJOR.MINOR.PATCH：

  • MAJOR：不兼容的 API 变更
  • MINOR：向后兼容的功能新增
  • PATCH：向后兼容的问题修正

范围（range）描述的是一组满足条件的版本集合；npm install 在集合内选取满足范围的最高版本（有 lock 文件时以 lock 为准）。在线验证：Version range syntax examples (opens new window)

# 版本范围符号

写法 含义
1.2.3 精确版本
^1.2.3 锁主版本（1.x.x），npm 默认，推荐
~1.2.3 锁次版本（1.2.x）
>=1.2.3 <2.0.0 范围组合
1.2.3 - 2.3.4 闭区间
1.2.3 \|\| 2.3.4 或关系
* / latest 任意 / 最新（避免使用）
git+https://github.com/user/repo.git Git 仓库
file:../local-package 本地路径

预发布版本（如 1.2.3-beta.1）默认不会被 ^1.2.3 选中，除非范围本身带 -beta 或显式安装对应 dist-tag——即 npm 不会自动把测试版带进项目。

# 常见问题

# node/npm 版本不兼容

用 nvm 隔离多版本：

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
nvm install 18 && nvm use 18
nvm alias default 18    # 设默认版本
nvm ls                  # 已装版本

# 方法1（推荐）：用 nvm 管理的 node 不需要 sudo
# 方法2：改全局安装目录

echo 'export PATH=~/.npm-global/bin:$PATH' >> ~/.bashrc

# 最佳实践

  1. 提交 package-lock.json，CI/服务器用 npm ci 安装——严格按 lock、可重现
  2. 版本范围：默认 ^；避免 * / latest；确需锁死用精确版本
  3. 区分依赖类型：运行时进 dependencies，构建/测试工具进 devDependencies
  4. 定期更新：npm outdated → npx ncu -u → npm i → npm test 回归
  5. 钩子自动化：prepublishOnly 防误发布，prepare 自动装 hooks，postversion 自动推 tag
