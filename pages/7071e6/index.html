    git 使用指南

    这是一份“命令优先、可快速检索”的 Git 速用指南。
    如果你在找 log，直接跳到 ## 1. command > ### 1.2 log。

    • Learn Git Online (opens new window)
    • Git 官方文档 (opens new window)

    # 0. 核心概念（精简）

    # 0.1 三区模型

    1. 工作区（Working Directory）：你正在改的文件
    2. 暂存区（Staging Area）：准备提交的变更
    3. 仓库（Repository）：提交历史
    Untracked -> git add -> Staged -> git commit -> Committed
    1

    # 0.2 HEAD 与引用

    • HEAD：当前分支或当前提交指针
    • HEAD~1：上一个提交
    • HEAD^2：合并提交的第二父提交

    # 0.3 第一父路径（first-parent）

    • first-parent 表示：遇到 merge commit 时，只沿着“当前主线分支”的父提交继续回溯。它适合查看主分支的演进，不被功能分支内部提交干扰。
    # 只看主线提交历史
git log --first-parent --oneline

# 忽略所有繁杂的开发细节，只按时间线列出最近合并进来的 Pull Request（PR）或分支合并历史
#   <number>: 限制显示
#   <branch>: 指定目标分支
git log --first-parent --merges --oneline -n <number> <branch>

# 统计主线提交数量
git rev-list --first-parent --count main

    举例

    HEAD → M → B → A
    1
    main:    A ── B ──────────────── M ── HEAD
                                 ↑
                         只走这条线，忽略右边合并进来的
    1

    --first-parent 的视角：merge 只是主线上的一个普通节点，合并进来的分支完全不可见。

    # 0.4 祖先路径（ancestry-path）

    从目标 commit 出发，能追溯到它的所有路径上的节点。

    假设目标是 commit D，问"D 如何到达 HEAD？"：

    D → E → F → M → HEAD
    1
    main:    A ── B ──────────────── M ── HEAD
                                ╱
feature:        C ── D ── E ── F
                      ↑
                   目标 commit
    1
    2
    3
    4
    5

    --ancestry-path 只保留从 D 通往 HEAD 的路径，A B C 这些不在路径上的全部排除。

    # 1.1.7 rebase vs merge

    场景 merge rebase
    历史记录 保留完整合并节点 线性历史，更干净
    冲突解决 一次解决 可能要多次解决
    公共分支 ✅ 推荐 ❌ 不要在 main 上 rebase
    本地 feature 分支 可以 ✅ 推荐，保持干净
    # 同步主分支（本地 feature 推荐 rebase）
git fetch origin
git rebase origin/main

# 解决冲突后继续
git rebase --continue
git rebase --abort    # 放弃 rebase，回到之前状态

# merge 方式
git fetch origin
git merge origin/main

    # 1.5 rev-parse

    git rev-parse 是一个功能非常强大的底层工具，主要用于将各种 Git 对象名、引用或标志解析为可用的格式（例如具体的 Hash 值或路径）。

    最常用的几个参数：

    1. 解析引用（最常用）

    • git rev-parse <branch_name>：获取指定分支或提交的完整 SHA-1 哈希值
    • git rev-parse --abbrev-ref <ref>：获取引用的简短名称（例如直接得到当前分支名）
    • git rev-parse --short <commit>：获取短哈希值

    2. 路径与环境信息

    • git rev-parse --show-toplevel：返回 Git 仓库的根目录绝对路径（写脚本时常用）
    • git rev-parse --git-dir：返回 .git 目录的路径
    • git rev-parse --is-inside-work-tree：检查当前目录是否在 Git 工作区内（返回 true / false）

    3. 其他常用标志

    • --verify <ref>：校验引用是否存在（失败则非 0 退出，适合脚本判断）
    # 当前提交 hash
git rev-parse HEAD
git rev-parse --short HEAD

# 当前分支名（detached HEAD 时输出 HEAD）
git rev-parse --abbrev-ref HEAD

# 把任意引用解析为 hash
git rev-parse main
git rev-parse origin/main
git rev-parse v1.2.0

# 父提交（^ 与 ~1 等价）
git rev-parse HEAD^
git rev-parse HEAD~1

# 仓库根目录（写脚本、拼路径时常用）
git rev-parse --show-toplevel

# 是否在 git 工作区内
git rev-parse --is-inside-work-tree

# 校验引用是否存在（失败则非 0 退出，适合脚本判断）
git rev-parse --verify main

    # 1.6 worktree

    一个 Git 仓库可以同时检出多个分支到不同目录，共享同一份 .git 历史。适合并行开发多 feature、紧急 hotfix 不打断当前工作、PR 本地 review。

    # 1.6.1 核心概念

    • 主工作区：git clone 得到的原始目录，通常绑定 main 分支
    • 附加工作区：通过 git worktree add 创建的目录，绑定其他分支
    • 共享：所有 worktree 共享同一个 .git 对象库，提交/分支对所有 worktree 立即可见
    • 隔离：每个 worktree 有独立的工作区文件，改文件互不影响
    repo/                    ← 主工作区，main 分支
├── .git
├── src/
└── ...

repo-feature/            ← 附加工作区，feature/xxx 分支
├── src/
└── ...

    # 1.6.2 常用命令

    # 列出所有 worktree（路径 + 分支 + commit）
git worktree list

# 基于已有分支创建 worktree
git worktree add ../repo-feature feature/xxx

# 基于 main 创建新分支并检出到 worktree
git worktree add -b feature/xxx ../repo-feature main

# 基于某个 tag/commit 创建 worktree（detached HEAD）
git worktree add ../repo-v1.0.0 v1.0.0

# 删除 worktree（工作区干净时）
git worktree remove ../repo-feature

# 强制删除（有未提交改动时，会丢弃改动）
git worktree remove --force ../repo-feature

# 清理已被手动删除目录的 worktree 记录
git worktree prune

    # 1.6.4 注意事项

    • 依赖安装：每个 worktree 有独立的 node_modules，需要重新 npm install / yarn，或从主工作区复制
    • 环境变量：.env、.envrc 等文件在每个 worktree 中独立，需单独配置
    • 端口冲突：多个 worktree 同时跑 dev server 会端口冲突，需改端口
    • 同一分支不能同时检出：Git 不允许两个 worktree 检出同一个分支（会报 is already checked out）
    • 删除前确认：git worktree remove 前确认改动已提交或备份，--force 会丢弃未提交改动

    # 1.7 hooks（钩子）

    Git 在关键动作前后自动执行的脚本，存放在 .git/hooks/。把 sample 文件去掉 .sample 后缀（或新建同名可执行文件）即生效；脚本退出码非 0 则中断该动作。

    # 1.7.1 常用客户端 hooks

    hook 触发时机 典型用途
    pre-commit git commit 执行前 lint / 格式检查 / 拦截大文件、敏感信息
    prepare-commit-msg 提交信息模板生成后 自动填充模板、注入分支号
    commit-msg 提交信息写完后 校验 Conventional Commits 规范
    post-commit 提交完成后 通知、统计
    pre-push git push 执行前 跑测试、阻止向 main 直推
    post-merge merge / pull 完成后 自动同步依赖（npm install 等）

    服务端 hooks（pre-receive / post-receive）部署在远端仓库，用于 CI 拦截和权限校验，日常开发较少直接接触。

    # 1.11 partial clone 与 sparse checkout

    GitHub 支持 Git 的 partial clone，不需要专用 GitHub 命令。常用参数是 git clone --filter=blob:none：先获取所需历史中的提交和目录树，文件内容（blob）按需下载；它不是只克隆某个目录。

    机制 控制什么 不代表什么
    --filter=blob:none 延迟下载文件内容，使用时从远端补取 不是禁止下载某些文件，也不是目录权限控制
    --depth=1 只获取浅层提交历史 不限制当前版本包含哪些文件
    --sparse / git sparse-checkout 限制哪些跟踪文件出现在工作目录 单独使用不保证对应内容没有进入本地对象库
    --no-checkout 克隆后暂不生成工作目录中的跟踪文件 单独使用仍可能下载全部对象

    可执行例子：先不取文件内容，再选择目录

    下面使用公开的 actions/checkout 仓库及其 v4 标签，在新目录中执行，不修改已有项目。检出标签会进入 detached HEAD，适合本例阅读和验证；需要开发时另建分支。

    # 克隆提交和目录树，暂不检出文件；这里没有使用 --depth，仍可查看该版本历史
git clone --filter=blob:none --no-checkout --single-branch --no-tags \
  --branch v4 https://github.com/actions/checkout.git checkout-partial-demo
cd checkout-partial-demo

# 配置需要的目录，再检出；缺少的文件内容由 Git 自动补下载
git sparse-checkout set --cone src
git checkout v4

# 扩大选择范围；新增目录需要的内容也可能触发下载
git sparse-checkout add __test__
git sparse-checkout list

    cone 模式会保留仓库根目录的文件以及所选目录路径上的父目录文件，不是“严格只取 src”；这里的选择范围是 src 与随后加入的 __test__，不要把这一示例当作私人目录隔离规则。

    更短的组合是 git clone --filter=blob:none --sparse <URL> <新目录>，再运行 git sparse-checkout set --cone <目录>；初始检出会取根目录文件。单独执行 git clone --filter=blob:none <URL> 时，默认 checkout 仍会下载当前版本所需的文件，主要省下暂时未用到的历史文件内容。

    “尚未获取的对象”具体指什么

    Git 用对象 ID 保存数据：commit 表示提交，tree 记录文件名、目录结构与对象引用，blob 保存一份文件内容。blob:none 允许本地已有目录树，但其中一些 blob 尚未下载。

    例如先只检出 src、还没有执行上面的 add __test__ 时，Git 已知道 __test__/input-helper.test.ts 在哪个提交中存在及其 blob ID，但不一定已有它的内容。下面的命令需要读取内容，可能自动向 GitHub 补下载；它不会把该文件写进工作目录：

    git show HEAD:__test__/input-helper.test.ts
    1

    所以“目录里没有文件”和“对象库里没有文件内容”不同：git show 可能已经取回内容，但 sparse checkout 仍不把文件放进工作目录。修改选择范围、切换提交、查看历史 diff 等操作，也可能需要补下载；尚未下载的内容不能保证离线访问。

    检查 partial clone 是否生效

    git config --get remote.origin.promisor           # 通常为 true
git config --get remote.origin.partialclonefilter # blob:none

# 列出当前可达对象及缺失对象；? 开头表示尚未获取的对象 ID
git rev-list --objects --all --missing=print

    promisor remote 可以理解为“答应在需要时补发对象的远端”。这里的缺失是 partial clone 允许的状态，不等于仓库损坏；访问所需对象时若补下载失败，该次操作仍会失败。

    为什么私有仓库 CI 的第二次 checkout 也需要认证

    actions/checkout@v4 在设置 sparse-checkout、且没有显式设置其他 filter 时，会使用 blob:none 获取对象。第一次只检出配置文件，后续扩大范围到公开文档时，需要从私有仓库补取尚未下载的内容。私有仓库中的“公开文档”仍受仓库权限保护，补下载同样需要认证。

    permissions:
  contents: read

steps:
  - uses: actions/checkout@v4
    with:
      persist-credentials: true
      sparse-checkout: |
        .github/config
        scripts/docs
      sparse-checkout-cone-mode: true

    这里保留只读 GITHUB_TOKEN 的认证配置，供后续 Git 命令补下载；checkout 的 post-job 步骤会清理认证。设置 persist-credentials: false 又未提供其他认证时，后续请求可能报 could not read Username 或 could not fetch ... from promisor remote。这不是要求提高令牌权限，也不是 Node 或依赖安装问题。

    本项目仍需读取发布黑名单后，按排除规则扩大 sparse checkout；不能用 git sparse-checkout disable 绕过错误，因为它会恢复所有跟踪文件。排除发布也不是仓库访问权限：有仓库读取权限的人仍可单独读取未检出的路径；partial clone 不负责保密。不要把令牌直接写进 clone URL 或日志。
