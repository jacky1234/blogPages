ln、readlink 与 realpath：创建链接、解析路径和排查失效

# 📖 简介

ln 是 Linux/macOS 下的链接创建命令，分为：

  • 软链接（Symbolic Link）：类似 Windows 的快捷方式，指向原文件路径
  • 硬链接（Hard Link）：多个文件名指向同一个 inode

# 📝 语法

ln [选项] 源文件 目标文件
1

# 创建、查看与删除链接

ln 创建链接，readlink 读取软链接中保存的目标路径。硬链接没有一个独立的“目标路径”可供读取，不能用 readlink 找它的“源文件”。

操作 命令 说明
创建软链接 ln -s target.txt shortcut 创建名为 shortcut 的入口，指向 target.txt
创建硬链接 ln target.txt another.txt 给同一个文件增加目录项
查看保存的目标 readlink shortcut 输出链接中保存的路径字符串，不保证目标存在
解析最终路径 readlink -f shortcut 跟随链接链，输出规范化的绝对路径；需确认本机支持
解析路径（不限于软链接） realpath shortcut 解析各级软链接、. 和 ..，输出最终绝对路径；参数和缺失路径行为需确认本机实现
查看链接本身 ls -ld shortcut 观察 shortcut -> target.txt，不能据此证明目标有效
替换已有软链接 ln -sfn new-target shortcut -f 替换目标；-n 避免跟随目标位置的“目录软链接”
删除链接入口 unlink shortcut 删除入口，不删除其指向的文件；路径末尾不要加 /

readlink -h 和帮助参数

本机 macOS 自带 readlink 的用法是 readlink [-fn] [file ...]，-h 会报非法参数。参数不是所有命令通用的，不能把 -h 一律当作 help。查阅 GNU readlink 手册 (opens new window) 时，也需先确认正在使用哪个实现。

命令／参数 本机 macOS 自带实现 GNU 实现（常见于 Linux）
查看帮助 man readlink、man ln readlink --help、ln --help，也可用 man
readlink -h 不支持 GNU 文档未定义此短选项，使用 --help
readlink -n shortcut 不在结果末尾输出换行 同左
readlink -f shortcut 本机支持；部分旧版 macOS 不支持 支持，解析路径中各级软链接
ln -h 不跟随目标位置的软链接，常配合 -sf 替换目录软链接；-n 同义 使用 -n；不要照搬 BSD 的 -h

脚本优先用 ln -sfn 表达“不跟随目标目录软链接”。-n 不会把一个真实目录强行当作普通链接位置：目标若是真实目录，ln 仍可能在目录内创建链接；GNU 的 -T 可明确按链接名处理，但不能直接照搬到 macOS。

readlink -f 的缺失路径处理也应按实现核对。GNU -f 允许最后一个路径组件不存在，其余组件需可解析；需要所有组件存在时，GNU 有 -e，但 macOS 自带实现不一定支持。因此，不能把 readlink -f 成功直接当作目标存在的判断。

readlink、readlink -f 与 realpath

命令 读取／解析方式 普通文件或目录
readlink path 读取入口软链接保存的目标字符串，不继续解析目标 输入不是软链接时失败
readlink -f path 规范化路径，跟随路径中各级软链接，输出绝对路径 可以解析；需确认支持 -f
realpath path 默认解析各级软链接及 .、.. 等，输出规范化的绝对路径 可以解析，不要求入口是软链接

例如本仓库部署的命令入口：

readlink "$HOME/.local/bin/ux"
realpath "$HOME/.local/bin/ux"
1
2

如果 ux 保存的是直接指向仓库 assets/files/com.shell.useful/ux.sh 的绝对路径，且该目标路径无需进一步解析，两条命令输出会相同。前者读取保存的字符串，后者计算最终路径；输出相同不代表作用相同。相对目标或多层链接则能体现区别，见下面的演示。

本机 macOS 的 realpath 用法是 realpath [-q] [path ...]，通过 man realpath 查询；不要直接照搬 GNU 的 -e、-m 等参数。旧系统也应先用 command -v realpath 确认命令可用。缺失路径的处理取决于实现和选项，不能仅凭输出了绝对路径就认定目标存在；判断目标仍用 [ -e "$path" ] 并检查退出状态。

相对目标、链式链接与悬空链接

在一个空的演示目录中执行：

mkdir -p actual links
printf 'hello\n' > actual/data.txt
ln -s ../actual/data.txt links/first
# 
ln -s first links/second

readlink links/first
# ../actual/data.txt
readlink links/second
# first

# 本机支持 -f 时，会输出当前演示目录下 actual/data.txt 的绝对路径
readlink -f links/second

# 本机提供 realpath 时，得到同一个最终绝对路径
realpath links/second

# 普通文件也可以解析
realpath actual/../actual/data.txt

相对目标是相对于链接所在目录解析，不是相对于执行 readlink 时的工作目录。上例中 links/second 保存的是 first，系统从 links/ 中继续寻找 first，再解析到 actual/data.txt。普通 readlink 只显示保存的那一段，不会自动读完整条链。

悬空链接也能读到保存的目标：

ln -s not-created.txt links/missing
readlink links/missing
# not-created.txt

[ -L links/missing ] && echo '入口是软链接'
[ ! -e links/missing ] && echo '目标当前不可解析或不存在'

# 🆚 软链接 vs 硬链接

特性 软链接（-s） 硬链接
是否可以跨文件系统 ✅ 可以 ❌ 不可以
是否可以链接目录 ✅ 可以 ❌ 不可以
删除原文件后 链接失效（悬空链接） 链接仍有效（数据仍在）
inode 新的 inode 和原文件相同 inode
适用场景 目录、跨分区、快捷方式 文件备份、节省空间

# 🆚 硬链接 vs Copy

一句话：硬链接是同一份数据多一个名字，Copy 是数据复制一份、从此互不相干。

特性 硬链接 Copy（cp）
inode 相同（指向同一份数据） 不同（数据完整复制一份）
磁盘占用 几乎为 0（只新增一条目录项） 数据占多少就翻多少
内容是否同步 ✅ 改一处处处可见（本质是同一个文件） ❌ 复制后各自独立、互不影响
删除原文件后 链接仍有效（引用计数 -1，数据不删） 不影响（本来就是两份）
元数据（权限/时间戳） 共享同一套 各自独立
适用场景 去重、增量备份（如 rsync --link-dest） 独立快照、真正的备份

验证：

echo "hello" > a.txt
ln a.txt b.txt     # 硬链接
cp a.txt c.txt     # 复制

ls -i a.txt b.txt c.txt
# a.txt、b.txt 的 inode 相同；c.txt 不同
# ls -l 第二列的数字 = 指向该 inode 的硬链接数

echo " world" >> b.txt
cat a.txt          # hello world —— 硬链接同步变化
cat c.txt          # hello —— 复制不受影响

# ⚠️ 注意事项

# 1. 相对路径 vs 绝对路径

  • 用相对路径创建的软链接，移动目录后可能失效
  • 用绝对路径创建的软链接，移动源文件后失效

# 2. 相对路径的计算

  • 相对路径是相对于链接所在目录，不是当前目录

检查链接是否有效

link='shortcut'
if [ -L "$link" ]; then
  if [ -e "$link" ]; then
    echo '软链接存在，目标存在'
  else
    echo '软链接存在，但目标不存在或当前不可解析'
  fi
else
  echo '该路径不是软链接，或入口不存在／不可访问'
fi

批量查找目标不存在或不可解析的软链接

环境 命令
GNU find，默认不跟随软链接 find . -xtype l
macOS／GNU find 可用的写法 find . -type l ! -exec test -e {} \; -print

macOS 自带 find 不应直接假定支持 GNU 的 -xtype。第二条命令先选出软链接，再检查其目标；结果也可能包含权限或循环导致的不可解析路径，不能全部归因为文件被删除。
